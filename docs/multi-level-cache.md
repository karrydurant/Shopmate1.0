### 缓存中存储的内容有什么

##### 长缓存(Redis 存 JSON，Caffeine 本地存对象)

key：`product:detail:v2:{spuId}`

TTL：Redis侧 1 小时 + 0~600s 随机抖动，本地 Caffeine 30s

```plaintext
{
    "v": 版本号,
    "n": true/false,
    "d": {...详情 VO...}
}
```

##### 短缓存(库存/销量短快照，只存在于 Redis)

```plaintext
Key：product:stock:{spuId}
内容：Snapshot 快照对象
TTL：5 秒
```

### 为什么不把库存/销量也放进 1 小时的长缓存？

商品详情里有两类字段，变更频率和缓存诉求完全不同，所以拆成两份缓存：

1.静态字段：标题、价格区间、SKU 属性、主图、类目。偶尔修改，适合 1 小时长缓存

2.易变字段：库存、销量。下单锁定、支付扣减、取消归还、退款回补时高频变化，适合 5 s 短缓存

如果把库存/销量塞进 1 小时的长缓存，数据高频变化，就要频繁地失效整个长缓存(删缓存简单、幂等、不造脏数据，改缓存要处理并发和两级同步)，热点商品就会反复出现缓存击穿问题。

所以做法是把库存、销量单独拆成一份短 TTL 快照，查库的瞬间，把每个 SKU 的库存读成 `skuId → 库存` 映射，各 SKU 销量求和成一个总销量，打包成快照，写进 Redis，5 秒内就一直用这份数字，不会跟着订单链路的实时扣减、归还再变，5 秒后快照过期，下一次有人读，再重新查一次库，生成一份新的快照。

要展示商品信息时，先把长缓存里的共享 VO 深拷贝出一份副本，用快照覆盖副本对应字段，再返回副本。

### 这份库存/销量数据是实时的吗，最长会延迟多久，为什么可以接受这个延迟？

最长会延迟 5 s，业务上，库存差个几秒通常不影响导购浏览，真正扣减库存、防超卖，走的是下单时数据库侧的原子条件更新，这份数据仅用于展示。

通过这个设计带来了长期稳定性：静态详情不被订单链路反复击穿，热点商品扛得住流量。

### Redis、DB 故障降级路径

##### Redis 不可用但 DB 正常

1. 读 Redis 详情正文：读失败按「未命中」处理，不报错，请求继续往下走：布隆判断 → 加锁 → 回源 DB。

2. 读版本号，版本号存在 Redis，读不到就返回 null，本次 DB 结果照常返回给用户，但跳过缓存回填（不写 Redis、不写本地）；
- 原因：拿不到版本就无法判断数据新旧，宁可这次不缓存，也不把旧值写进去。

3. 库存快照，快照读 Redis 失败，降级直接查 DB 生成，快照写回 Redis 失败也只记日志，下次读再查库。

4. 分布式锁，锁基于 Redis，Redis 挂了大概率抢不到锁，按「抢不到锁」处理：降级直读 DB，只读不写缓存。

##### 二者同时不可用

只有本地 Caffeine 里最近 30 秒访问过的热点商品还能命中

### 缓存穿透一般怎么解决？布隆过滤器的原理是什么，它为什么会有误判，能不能删除元素？你在启动阶段如果数据库抖动导致布隆预热失败，这时候还能不能用布隆拦截？为什么？

用布隆过滤器(布隆参数：预期 10 万商品、误判率 1%)。

布隆过滤器是一种空间高效的概率型集合结构，用来快速判断 "一个 ID 有没有可能存在"。
判定 "不存在" 就一定 "不存在"，判定 "存在"只是可能存在，仍要回源 DB 确认。

底层是一个 bit 数组 + 多个哈希函数。
添加元素时用 k 个哈希函数算出 k 个位置，把对应 bit 置 1。
查询元素时同样算 k 个位置，有任意一个 bit 是 0 → 一定不存在。
一个 bit 位可能被多个元素共享，所以不能安全地移除某个元素；
不存在的元素，其哈希位恰好都被别人置 1，会被误判为存在。

之所以一定要预热成功才能用于拦截是因为：如果过滤器还没从 DB 把真实 ID 装载进来，bit 位几乎全是 0，绝大多数真实商品都会被误判成「不存在」。

另外由于布隆不能移除元素，所以通过定时整体重建过滤器(构建成功才整体替换)来对齐 DB

### 查一个不存在的商品 ID，怎么防止它每次都打到数据库？负缓存存在 Redis 里用什么标识「这是空结果」？

负缓存+布隆过滤器。负缓存是指 DB 里查不到对应商品时，把 "不存在" 这个结论也缓存下来。

项目中缓存信封(内存中存对象，Redis 中存 JSON 字符串)是 `{v: 版本, n: 是否负缓存, d: 数据}` 结构：负缓存用信封里的 `detail == null` 表示，`n = true` 标记 

### 为什么负缓存的过期时间要比正缓存短，短到多少合理？如果负缓存没清，新上架的商品会发生什么？

负缓存 TTL：60 秒；正缓存 TTL：1 小时 + 0~600 秒随机抖动(防雪崩)。

60 s 既能挡住短时间内对无效 ID 的反复穿透，又不会把新商品挡太久。

走正规写路径的新商品，写库提交后会主动清掉这条负缓存；只有绕过写路径直接改库，才需要等这 60 秒过期

### 什么是缓存击穿？单机的 synchronized 为什么解决不了集群下的击穿问题？

缓存击穿指的是：某个热点商品的缓存刚好失效（过期或被删），一瞬间大量并发请求同时发现缓存没命中，一起回源打到数据库，DB 瞬时承压，可能被压垮。

`synchronized`、`ReentrantLock` 这类 JVM 锁，锁的是单个进程内的对象监视器，互斥范围只在这一台实例内部。
集群部署时有 N 台实例，请求被负载均衡分散到不同机器，每台实例内部都串行，但跨实例之间互不感知，结果 N 台机器各自放一批线程同时打 DB，击穿照样发生。要让所有实例在同一把锁上排队，必须有一个所有实例都能访问的共享存储来协调 —— 这里用 Redis + Redisson。

### 分布式锁的粒度、等待时间、持锁时间分别是怎么考虑的？

项目中分布式锁是商品粒度（只互斥同一个商品的并发回源，不同商品之间不互相阻塞）

等待时间 1000 ms（一次 DB 回源通常毫秒级，正常情况下持锁线程很快释放，后来者短时间内就能等到，设太长会让请求线程排队积压）

持锁时间 10000 ms（必须显式传 leaseTime，不传的话 Redisson 看门狗会后台持续给锁续期，一直续到进程结束；一旦某条路径漏了 unlock，这个商品的锁就永久不释放，别人永远抢不到。10 秒覆盖一次 DB 查询 + 缓存回填的正常耗时足够，又能在持锁线程出问题时兜底自动释放。）

### 拿到锁之后为什么还要再查一次缓存？

之所以要 Double-Check 是因为：线程在等锁期间可能已经有回源线程把缓存回填了，如果拿到锁直接再查 DB，就重复回源了。Double-Check 发现 Redis 已有值就直接返回，不再查 DB。

### 如果一直抢不到锁会怎么处理？

抢锁失败，log.warn 记录锁竞争，loadFromDB(productId) 直读 DB 返回。

抢不到锁不代表商品不存在，说明有人正在回源，降级直读 DB，不回写缓存（实现兜底保可用的目的就够了）

### 最前面那层本地缓存是用什么实现的，容量和过期时间怎么配置的？为什么要有本地缓存这一层？本地缓存的局限是什么？

本地缓存是部署在应用进程内存里的一层缓存(存储商品详情和版本号)，本项目用 Caffeine 实现。最多 5000 条商品详情/版本号，商品详情写入后 30 秒过期，版本号则是 10 分钟。

容量 5000：本地缓存只扛热点，全量商品放不进 JVM 内存，超出按 W-TinyLFU 淘汰冷门条目

过期 30 s：本地缓存多实例间同步比较困难，设置为 30 s 既能挡住瞬时重复读，又压低了一致性风险

##### 本地缓存的作用

1.提升速度：读的是 JVM 内存，不走网络，没有 Redis 往返延迟，热点商品直接命中返回

2.减轻 Redis 压力：高频重复读在本地就挡掉了，不用每次都打 Redis

##### 本地缓存的局限

1.多实例间并不同步

2.容量受 JVM 内存限制，不能放全量数据，只缓存热点

3.进程重启缓存就空了，冷启动后要重新回源预热

### 集群部署下本地缓存的数据一致性怎么保证？

1.写路径主动失效本实例 + 广播通知其它实例

写库事务提交后：Redis 版本 +1、通过 Lua 原子命令删除商品正文数据->清理实例本地 Caffeine->RocketMQ 广播变更事件，其他实例收到后清各自本地缓存

2.版本号 + 本地 "水位线" 兜底

广播消息有到达延迟，并发下可能出现

### 什么是"水位线"？为什么要有它？

水位线是本实例在本地内存维护的一张表：

每个商品在 Redis 里有一个版本计数器，写一次数据版本就 +1。缓存信封里也带着写入时的版本号。

设想一个场景：

线程 A 从 DB/Redis 读到一个旧版本数据，准备写本地缓存，线程 B 收到失效事件，清掉本地旧条目，线程 A 才把手里那份旧值 put 进本地缓存

结果就是本地缓存又留下一条旧值，而且没有后续事件再来修它，只能等 30 秒 TTL。本地缓存虽然短，但这个窗口内读到的就是脏数据。

水位线是一条过期判定标准：**待写入（或已缓存）条目的版本号 ≤ 水位线，说明这是已失效的旧数据，拒绝。**

##### 项目中用到 "水位线" 的地方

**1. 读本地时校验**（`readLocal`）：缓存条目版本 < 水位线，说明已被更新的失效淘汰，清掉按未命中处理。

**2. 写本地前校验**（`localFill` 第一次检查）：水位线已高于待写入版本，直接放弃写入。

**3. 写本地后再校验**（`localFill` 第二次检查）：覆盖「第一次检查之后、put 之前」恰好到达失效事件的窗口；若水位线已变高，立即删掉刚写的条目。

### 介绍一下缓存击穿，是怎么解决的？

把 "查 DB + 回填缓存(Redis + 内存)" 这个动作变成同一时刻只有一个请求能做，防止缓存击穿（即一瞬间有大量请求同时进来查这个商品，DB 连接池瞬间被打爆）

### 热点商品缓存失效的瞬间你怎么避免大量请求同时打到数据库？加了分布式锁之后，拿到锁为什么还要再查一次缓存？

采用旁路缓存模式(Cache Aside)。读的时候缓存里没有就回源 DB 再写缓存；写的时候先更新数据库，再删除缓存。

#### 为什么是删除缓存，而不是更新缓存

1.缓存值是多表聚合的视图（SPU + 多个 SKU 拼出来的 VO），改一个 DB 字段要精确更新整个 VO，不如删了让下次读请求重新拼

2.直接更新缓存有并发竞态：两个写请求交错时，缓存和 DB 的顺序可能反
