## 问题

### 商品详情缓存里库存和销量是怎么处理的？为什么不把库存也放进 1 小时的详情缓存？这份库存数据是实时的吗，最长会延迟多久，为什么可以接受这个延迟？

商品详情里有两类字段，变更频率和缓存诉求完全不同，所以拆成两份缓存：

1.静态字段：标题、价格区间、SKU 属性、主图、类目。偶尔修改，适合 1 小时长缓存

2.易变字段：库存、销量。下单锁定、支付扣减、取消归还、退款回补时高频变化

如果把库存塞进 1 小时的详情长缓存，库存数据高频变化，就要高频地失效整个详情缓存(因为详情缓存是整条商品打包成一个对象存的)，热点商品就会反复出现缓存击穿问题。

所以做法是把库存、销量单独拆成一份短 TTL 快照

### 缓存穿透一般怎么解决？布隆过滤器的原理是什么，它为什么会有误判，能不能删除元素？你在启动阶段如果数据库抖动导致布隆预热失败，这时候还能不能用布隆拦截？为什么？

用布隆过滤器。布隆过滤器是一种空间高效的概率型集合结构，用来快速判断 "一个 ID 有没有可能存在"。判定 "不存在" 就一定 "不存在"，判定 "存在"只是可能存在，仍要回源 DB 确认

底层是一个 bit 数组 + 多个哈希函数。添加元素时用 k 个哈希函数算出 k 个位置，把对应 bit 置 1。查询元素时同样算 k 个位置，有任意一个 bit 是 0 → 一定不存在。一个 bit 可能被多个元素共享，所以不能安全地移除某个元素；不存在的元素，其哈希位恰好都被别人置 1，会被误判为存在。

之所以一定要预热成功才能用于拦截是因为：如果过滤器还没从 DB 把真实 ID 装载进来，bit 位几乎全是 0，绝大多数真实商品都会被误判成「不存在」。另外由于布隆不能移除元素，所以通过定时整体重建过滤器来对齐 DB

### 查一个不存在的商品 ID，怎么防止它每次都打到数据库？负缓存存在 Redis 里用什么标识「这是空结果」？为什么负缓存的过期时间要比正缓存短，短到多少合理？如果负缓存没清，新上架的商品会发生什么？

负缓存+布隆过滤器。负缓存是指 DB 里查不到对应商品时，把 "不存在" 这个结论也缓存下来。

项目中缓存信封(内存中存对象，Redis 中存 JSON 字符串)是 `{v: 版本, n: 是否负缓存, d: 数据}` 结构：负缓存用信封里的 `detail == null` 表示，`n = true` 标记

### 什么是缓存击穿？单机的 synchronized 为什么解决不了集群下的击穿问题？

缓存击穿指的是：某个热点商品的缓存刚好失效（过期或被删），一瞬间大量并发请求同时发现缓存没命中，一起回源打到数据库，DB 瞬时承压，可能被压垮。

`synchronized`、`ReentrantLock` 这类 JVM 锁，锁的是单个进程内的对象监视器，互斥范围只在这一台实例内部。
集群部署时有 N 台实例，请求被负载均衡分散到不同机器，每台实例内部都串行，但跨实例之间互不感知，结果 N 台机器各自放一批线程同时打 DB，击穿照样发生。要让所有实例在同一把锁上排队，必须有一个所有实例都能访问的共享存储来协调 —— 这里用 Redis + Redisson。

### 分布式锁的粒度、等待时间、持锁时间分别是怎么考虑的？

项目中分布式锁是商品粒度（只互斥同一个商品的并发回源，不同商品之间不互相阻塞）

等待时间 1000 ms（一次 DB 回源通常毫秒级，正常情况下持锁线程很快释放，后来者短时间内就能等到，设太长会让请求线程排队积压）

持锁时间 10000 ms（必须显式传 leaseTime，不传的话 Redisson 看门狗会后台持续给锁续期，一直续到进程结束；一旦某条路径漏了 unlock，这个商品的锁就永久不释放，别人永远抢不到。10 秒覆盖一次 DB 查询 + 缓存回填的正常耗时足够，又能在持锁线程出问题时兜底自动释放。）

### 拿到锁之后为什么还要再查一次缓存？

之所以要 Double-Check 是因为：线程在等锁期间可能已经有回源线程把缓存回填了，如果拿到锁直接再查 DB，就重复回源了。Double-Check 发现 Redis 已有值就直接返回，不再查 DB。

### 如果一直抢不到锁会怎么处理？

抢锁失败，log.warn 记录锁竞争，loadFromDB(productId) 直读 DB 返回。

抢不到锁不代表商品不存在，说明有人正在回源，降级直读 DB，不回写缓存（兜底保可用即可）

##### 降级直读 DB 可能拿到旧值 / 中间态，返回给用户的库存、详情在那一刻可能和 DB 最新值有偏差。

偏差来源：读的过程中，正好有写提交

t1 查 SPU，t2 支付提交：SKU stock 100 → 70，t3 查 SKU：当前读读到 70

### 分布式锁 + Double-check 防的是什么？

把 "查 DB + 回填缓存(Redis + 内存)" 这个动作变成同一时刻只有一个请求能做，防止缓存击穿（即一瞬间有大量请求同时进来查这个商品，DB 连接池瞬间被打爆）

### 缓存和数据库怎么保持一致

采用旁路缓存模式(Cache Aside)。读的时候缓存里没有就回源 DB 再写缓存；写的时候先更新数据库，再删除缓存。

#### 为什么是删除缓存，而不是更新缓存

1.缓存值是多表聚合的视图（SPU + 多个 SKU 拼出来的 VO），改一个 DB 字段要精确更新整个 VO，不如删了让下次读请求重新拼

2.直接更新缓存有并发竞态：两个写请求交错时，缓存和 DB 的顺序可能反
